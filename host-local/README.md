# host-local — всё, что принадлежит этому хосту

Каталог существует только в ветке `host/uadmin-raider18` и не встречается
ни в одной ветке апстрима. Из этого следует главное его свойство: слияние
любого релиза `deepseek-ai/deepseek-harness` никогда не тронет ничего
отсюда — конфликтовать не с чем.

```
host-local/
├── docs/          документы этого хоста (release-log.md и всё остальное)
├── scripts/       start-web.sh и прочие локальные запускалки
└── state/         машинное состояние скриптов, не для чтения глазами
```

## Почему ветка называется без версии

Прошлая ветка звалась `pin/dsh-v0.1.2-rc.1`, и это ровно то, что делало
переезд на релиз болезненным: имя ветки кодировало версию, профиль dsh по
конвенции звался `web-<ветка>`, и каждый апгрейд требовал новой ветки, а
значит нового профиля — то есть переустановки ~700 МБ плагинов и потери
всего, что к профилю прирастает.

`host/uadmin-raider18` версию не кодирует. Идентичность ветки — «этот
хост», а не «этот релиз». Релиз меняется внутри неё слиянием тега.

## Профиль ровно один и зовётся `web`

Раньше `~/.dsh/start-web.sh` собирал имя профиля из имени ветки
(`web-${GIT_BRANCH}`) и при первом запуске на новой ветке копировал в него
базовый `web`. Каждая ветка получала собственную копию на 700+ МБ, дальше
жившую своей жизнью: правка `cordis.patch.yml` в одном профиле не была
видна другому, а market-кэш и настройки размазывались по каталогам.
Профилей накопилось четыре.

Всё сведено в `web`, остальные удалены, генерация `web-<ветка>` из
launcher'а вырезана. Изоляция теперь достигается веткой репозитория, а не
размножением профилей. **Не переименовывай профиль при апгрейде** — в этом
весь смысл конструкции.

## Релизы приходят тегами, не ветками

Апстрим не держит rc-веток: у `origin` есть только `master`. Релизы-кандидаты
существуют как теги — `dsh-v0.1.5-rc.2`, `dsh-v0.1.5-alpha.1` и так далее.
Поэтому `start-web.sh` ищет новое среди тегов `dsh-v*`, а не среди веток.

Новизна считается достижимостью, а не сравнением имён: тег, уже влитый в
ветку, новым не считается, как бы он ни назывался.

## Работа

```bash
host-local/scripts/start-web.sh            # fetch + pull + проверка + запуск
host-local/scripts/start-web.sh check      # только посмотреть, что вышло нового
host-local/scripts/start-web.sh status     # где мы сейчас
host-local/scripts/start-web.sh upgrade dsh-v0.1.5-rc.2
```

Переезд никогда не происходит сам. `start` и `check` только сообщают о
новых релизах и записывают факт появления в `docs/release-log.md`;
переход делает только явный `upgrade`.

Сам подъём сервера `start` делегирует в `~/.dsh/start-web.sh` — там
освобождение порта, ротация логов, обновление free-моделей OpenRouter,
починка абсолютных путей в agent-пресетах и рантайм-патчи под 0.1.2-rc.1.
Вторая реализация всего этого означала бы расхождение поведения, поэтому
здесь живёт только то, чего там нет: слежение за релизами.

Перед слиянием `upgrade` создаёт ветку `backup/uadmin-raider18-<дата>` —
откат одной командой `git reset --hard <эта ветка>`.

## Переменные окружения

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `DSH_HOST_BRANCH` | `host/uadmin-raider18` | ветка, вне которой скрипт откажется работать |
| `DSH_HOST_PROFILE` | `web` | профиль dsh; переживает апгрейды |
| `DSH_WEB_PORT` | `3000` | порт web |
| `DSH_UPSTREAM_REMOTE` | `origin` | откуда теги релизов |
| `DSH_FORK_REMOTE` | `fork` | личный форк |
| `DSH_RELEASE_TAG_GLOB` | `dsh-v*` | что считать релизом |

## Чего этот каталог не решает

Переносимость на другой хост. `host-local/` едет вместе с веткой, но
состояние dsh живёт вне репозитория — в `~/.dsh`, `~/.ouroboros`,
`~/.hindsight` и в целевых каталогах `link:`-зависимостей профиля. Это
отдельная задача, разобрана в `docs/dsh-docker.md` §9 корневого проекта.
