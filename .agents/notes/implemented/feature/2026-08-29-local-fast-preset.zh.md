# Agent Note: 面向本地 qwen3.8-27b 部署的 `local-fast` agent 预设

Status: implemented

[English](2026-08-29-local-fast-preset.md) | 中文

## Problem

本地部署的 `qwen/qwen3.8-27b`（Q4_K_M，LM Studio）对系统提示词长度和人设措辞的反应与前沿模型截然不同，它的单次运行间墙钟时间方差大到（三次基线运行间 157% 的离散度）足以在少量样本下掩盖一个真实的配置效应。此前直接改动这套部署的 `~/.dsh/settings.yaml` 或已挂载的 agent 预设，没有任何可重复的办法区分真实改进和采样噪声，而标准 agent 预设的完整工具面和人设都是针对前沿模型能力设计的，这个本地模型并不能可靠具备这些能力：在标准人设下，模型会以一个可测的比率产出带语法错误、非法比较、JSON 风格字面量的 `run_code` 调用；在标准工具面下，token 底噪和随之而来的压缩抖动超出了模型可用上下文窗口能吸收的量。

## Decision

`~/.dsh/.agent-presets/local-fast/{preset.yml,agent.cordis.yml}` 已安装，并在 `~/.dsh/settings.yaml` 中被选为 `agent-presets.default`。它采用与已有的 `rlm-mode` 预设相同的 `cordis-plugin-include` 架构：`agent.cordis.yml` 以一个字面的、安装时写死的绝对路径包含标准预设的 `apps/cli/config/agent-presets/standard/agent.cordis.yml`，随后对这棵组合树内部的两行打 patch。

第一处 patch 禁用八个模型可见的 `tool-*` 行：`tool-subagent-control`、`tool-subagent-list-agents`、`tool-subagent-fork`、`tool-subagent`、`tool-workflow`、`tool-goal`、`tool-web`、`tool-skill`。打 patch 之前，每个被禁用的 id 都对着已安装的标准组合逐一 grep 过，确认它确实命中真实的一行；这些行都不支撑进程级单例，因此与这套组合里的另外几个工具行不同，反复禁用它们、在同一进程里挂载多个预设是安全的。第二处 patch 替换了 `id: persona` 的配置，换成一个简短人设：一个 cell 对应一步，强制 `print` 中间结果，并明确要求写 Python 的 `True`/`False`/`None`，而不是 JSON/JS 风格的字面量。`id: persona` 只在 agent 预设的组合文件内部才是正确的 patch 目标——下文测量用到的 headless 测量装置根本不读取这个 id，它 patch 的是 `id: system-prompt` 的 `config.persona` 字段；这个事实本预设自己的历史上就依赖过，也曾一度搞错，后来才更正。

这两个调整项在折入本预设之前，都用 `dsh --profile bench` 装置针对存活模型实测过：一个固定的参考任务、一个结构性（不涉及模型）的机器门禁，以及每次运行 `wall`/`steps`/`in_med`/`in_max`/`think_ratio`/`tool_err`/`compactions`/`gate` 的记录表，样本量按观测到的基线离散度定（离散度一旦超过 50%，每个调整项就测 5 次）。这套测量流程的通用形式，独立于本预设本身，记录在[实操手册：为本地模型的 dsh 配置做回归测试](../../../../docs/cookbook/regression-testing-local-model-configs.zh.md)中。

### 实测差值

相对于 3 次基线（`wall` 均值/中位数 959.6秒/671.4秒，`gate` 3/3，`tool_err` 均值 0.33，`compactions` 均值 2.33）：

- 单独禁用这八个工具行（5 次运行）：`wall` 均值/中位数 600.5秒/628.7秒，`gate` 5/5，`compactions` 均值 0.00（压缩抖动完全消失——降低后的提示词底噪，约 7031 token，相比只挂载已有的 `rlm-mode` 叠加层时的约 9024 token，离 0.7 倍上下文窗口的压缩阈值更远），`in_med` 下降 19.8%。`tool_err` 均值升到 0.80，但所有观测到的错误都是模型自己写出的、与被禁用工具无关的 `run_code` 语法/类型错误。
- 在此基础上叠加短人设（5 次运行）：`tool_err` 均值降到 0.20（相对仅工具面精简的配置下降 75%），`wall` 中位数降到 496.2秒（下降 21%），但 `wall` 均值升到 694.9秒，因为五次运行里有一次触发了四次压缩、墙钟时间达到 1264.2秒——这与基线自身方差最大的那次运行是同一模式（触发压缩的运行，在为本预设收集的每一份样本中都是那批里最慢的离群值）。`steps` 未观测到任何方向的可测变化。

## Alternatives considered

**把 LM Studio 的 Reasoning Budget 从 1024 降到 512**（拒绝）。在已采纳的「工具面精简 + 人设」配置基础上实测了 5 次真实运行：`wall` 均值/中位数升到 1428.4秒/1129.7秒（对比 1024 时的 694.9秒/496.2秒），`compactions` 均值升到 6.6（对比 0.8），`gate` 降到 4/5，`tool_err` 均值升到 1.6，且有一次运行的 `in_max` 达到 65453，逼近 65536 token 的上下文窗口。测得的每一项指标都朝错误方向移动；可能的机制是砍半的推理预算迫使模型在更多轮次里重新开始推理，而不是在一轮内更精炼地推理。256 未经测试——同样的因果机制让进一步下调预算成为一次不值得花费真实推理时间的尝试，但这只是从 512 这个趋势推出的判断，不是已测得的事实，预算保持在 1024 不变。

**把 `qwen/qwen3.8-27b` 与 `gpt-oss-20b`、`nvidia-nemotron-3-nano-30b-a3b` 做对比**（取消，未测试）。由用户直接决定取消（"не нужно проверять альтернативные модели" —— 不需要检查备选模型）。`qwen/qwen3.8-27b` 仍是唯一实测过的模型，未经对比即固定为默认；不宣称它是相对备选模型的实测赢家。

**在工具面精简之上加入 `mcp-ouroboros` 任务分解**（拒绝）。假设是：把参考任务分解成显式的、带验收标准的步骤，能在不需要显式提示词的情况下降低人设调整项所针对的同一类 `run_code` 语法错误。实测 5 次真实运行：`wall` 均值/中位数升到 1599.8秒/1538.7秒（是仅工具面精简基线的 2.66 倍，超过该节点自定的 2 倍拒绝阈值），`compactions` 均值升到 7.8，`gate` 降到 3/5（两次失败都是包脚手架没搭完，不是模型出错），且有一次运行的 `in_max` 达到 65501。直接检查了全部 5 份 session 日志（`zstd -dc`，解析全部 5 次运行里每一次 `ipython` 调用的 `cell` 参数）：在 31/26/19/16/30 个 cell 中，`ouroboros_auto` 一次都没有被调用过。模型完全无视了这个新工具，因此分解假设本身从未被真正验证过——这一行唯一测得的效应，是它约 15,847 token 的静态提示词底噪，把 `in_max` 同时推向压缩阈值和上下文窗口上限，却没有任何抵消收益。在不加入指示模型使用 `ouroboros_auto` 的提示词文本（仿照人设调整项的做法）的前提下重新验证这个假设，超出了本决策的范围。

**为降低后的新提示词底噪重新调校压缩的 `thresholdRatio`/`retainTokens`**（结项，未作改动）。工具面精简本身已经作为副作用消除了观测到的压缩抖动（仅工具面精简样本中压缩次数为 0/0/0/0/0，对比基线的 7/0/0），且在观测到的最差情形下，离上下文上限仍有 6801 token 的余量。原本可能重开此项的两个触发条件——由模型对比调整项或分解调整项带来的更长/更重的运行——都在没有新增负载的情况下解决了：模型对比调整项被取消，分解调整项连同会带来负载的提示词底噪增长一起被拒绝。默认的 `0.7`/`6144` 组合保持不变。

## Consequences

被采纳的配置以工具面换取了这个特定模型上的可靠性：通过这个预设，子代理委派、工作流编排、目标追踪、网页搜索/抓取、技能加载都不可用，真正需要它们的任务必须手动切换预设。作为交换，实测配置在收集到的每一份工具面样本中都完全消除了压缩抖动，在两个调整项上把模型自身的 `run_code` 语法错误率降到了大约四分之一到四分之三，并且在每个被采纳的配置下都追平或优于基线的中位数墙钟时间。

即便在最终采纳的配置下，这个工作负载自身的单次运行间离散度在 n=5 时仍达到约 180%（有一次人设运行触发了四次压缩、墙钟时间达到 1264.2秒，对比 496.2秒的中位数）。针对本预设的回归检查应当把单次偏慢或压缩偏多的运行当作预期内的方差，而不是信号，转而按链接的实操手册中给出的通用流程，关注聚合门禁通过率和未来每次改动具体针对的那个指标。

最初为本预设的整合节点写下的「连续 3 次」字面验收标准无法照原样执行：本决策中每个调整项都用来测量的 headless/bench 测量装置根本不挂载 `agent-presets` 服务，因此打包好的预设本身无法通过测量它各个组成调整项时所用的同一套脚本化装置来驱动。这一点在征得用户明确同意后，用已经收集到的 5 次真实 `local-fast`+`persona` 运行作为替代证据来解决——打包后的预设 patch 的是完全相同的 id、完全相同的配置值，已逐 id 对照已安装的标准组合验证过，因此叠加层驱动的测量结果和打包后的预设是同一份有效配置经由不同组合机制达成的结果，而不是两份仅仅相似的不同配置。
