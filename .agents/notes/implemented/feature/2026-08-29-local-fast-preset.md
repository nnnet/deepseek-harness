# Agent Note: `local-fast` agent preset for a local qwen3.8-27b deployment

Status: implemented

English | [中文](2026-08-29-local-fast-preset.zh.md)

## Problem

A locally-hosted `qwen/qwen3.8-27b` (Q4_K_M, LM Studio) reacts to system-prompt size and persona wording very differently than a frontier model, and its run-to-run wall-time variance is large enough (157% spread across three baseline runs) to hide a real configuration effect at a handful of samples. Naively editing `~/.dsh/settings.yaml` or the mounted agent preset for this deployment had no repeatable way to tell a genuine improvement from sampling noise, and the standard agent preset's full tool surface and persona both target frontier-model capabilities this local model does not reliably have: the standard persona left the model producing `run_code` calls with syntax errors, disallowed comparisons, and JSON-style literals at a measured rate, and the standard tool surface added token floor and compaction churn the model's usable context window could not absorb.

## Decision

`~/.dsh/.agent-presets/local-fast/{preset.yml,agent.cordis.yml}` is installed and selected as `agent-presets.default` in `~/.dsh/settings.yaml`. It uses the same `cordis-plugin-include` architecture as the pre-existing `rlm-mode` preset: `agent.cordis.yml` includes the standard preset's `apps/cli/config/agent-presets/standard/agent.cordis.yml` by a literal, install-baked absolute path, then patches two rows inside that composition.

The first patch disables eight LLM-visible `tool-*` rows: `tool-subagent-control`, `tool-subagent-list-agents`, `tool-subagent-fork`, `tool-subagent`, `tool-workflow`, `tool-goal`, `tool-web`, `tool-skill`. Every disabled id was grepped against the installed standard composition before patching to confirm it names a real row; none of them back a process-wide singleton, so unlike some other tool rows in this composition, disabling them is safe to repeat across every preset mounted in one process. The second patch replaces `id: persona`'s config with a short persona: one cell per step, a mandatory `print` of the intermediate result, and an explicit instruction to write Python `True`/`False`/`None` rather than JSON/JS-style literals. `id: persona` is the correct patch target only inside agent-preset composition files — the headless surface that mounted the measurement harness (below) never reads this id at all; it patches `id: system-prompt`'s `config.persona` field instead, a fact this preset's own history depended on and got wrong once before correcting it.

Both levers were measured with a `dsh --profile bench` harness against the live model before being folded into this preset: a fixed reference task, a structural (non-model) machine gate, and a ledger of `wall`/`steps`/`in_med`/`in_max`/`think_ratio`/`tool_err`/`compactions`/`gate` per run, sized from the observed baseline spread (5 runs per lever once that spread exceeded 50%). The general form of this measurement procedure, independent of this specific preset, is documented in [Cookbook: regression-testing a local-model dsh configuration](../../../../docs/cookbook/regression-testing-local-model-configs.md).

### Measured deltas

Against the 3-run baseline (`wall` mean/median 959.6s/671.4s, `gate` 3/3, `tool_err` mean 0.33, `compactions` mean 2.33):

- Disabling the eight tool rows alone (5 runs): `wall` mean/median 600.5s/628.7s, `gate` 5/5, `compactions` mean 0.00 (compaction churn disappeared entirely — the reduced prompt floor, ~7031 tokens versus ~9024 with only the pre-existing `rlm-mode` overlay mounted, stays further from the 0.7-of-context-window compaction threshold), `in_med` down 19.8%. `tool_err` mean rose to 0.80, but all observed errors were unrelated `run_code` syntax/type bugs the model wrote on its own, not failures of any disabled tool.
- Adding the short persona on top (5 runs): `tool_err` mean fell to 0.20 (−75% against the tool-surface-only configuration), `wall` median fell to 496.2s (−21%), though `wall` mean rose to 694.9s because one of five runs hit four compactions and a 1264.2s wall time — the same pattern seen in the baseline's own highest-variance run (compaction-triggering runs are the slow outliers in every sample collected for this preset). `steps` did not measurably change either direction.

## Alternatives considered

**Lower the LM Studio Reasoning Budget from 1024 to 512** (rejected). Tested with 5 real runs at the already-accepted tool-surface-plus-persona configuration: `wall` mean/median rose to 1428.4s/1129.7s (versus 694.9s/496.2s at 1024), `compactions` mean rose to 6.6 (versus 0.8), `gate` fell to 4/5, `tool_err` mean rose to 1.6, and one run's `in_max` reached 65453 against a 65536-token context window. Every measured metric moved the wrong direction; the plausible mechanism is that a halved reasoning budget forces the model to restart its reasoning across more turns rather than reasoning more concisely in one pass. 256 was not tested — the same causal mechanism made further reduction an unpromising use of real inference time, but this is an inference from the 512 trend, not a tested fact, and the budget stays at 1024.

**Compare `qwen/qwen3.8-27b` against `gpt-oss-20b` and `nvidia-nemotron-3-nano-30b-a3b`** (cancelled, not tested). Cancelled by direct user decision ("не нужно проверять альтернативные модели" — no need to check alternative models). `qwen/qwen3.8-27b` remains the only measured model and is fixed as the default without a comparison; it is not claimed to be a measured winner over the alternatives.

**Add `mcp-ouroboros` task decomposition on top of the tool-surface reduction** (rejected). The hypothesis was that decomposing the reference task into explicit AC-steps would reduce the same `run_code` syntax-error class the persona lever targets, without needing explicit prompt text. Measured with 5 real runs: `wall` mean/median rose to 1599.8s/1538.7s (2.66× the tool-surface-only baseline, past the node's own 2× rejection threshold), `compactions` mean rose to 7.8, `gate` fell to 3/5 (both failures were incomplete package scaffolding, not model errors), and one run's `in_max` reached 65501. Every session log was inspected directly (`zstd -dc`, parsing the `cell` argument of every `ipython` call across all 5 runs): `ouroboros_auto` was never invoked once across 31/26/19/16/30 cells. The model ignored the new tool entirely, so the decomposition hypothesis itself was never exercised — the only measured effect of the row was its static ~15,847-token prompt floor, which pushed `in_max` toward both the compaction threshold and the context window ceiling with no offsetting benefit. Re-testing this hypothesis without prompt text instructing the model to use `ouroboros_auto` (in the spirit of the persona lever) is out of scope for this decision.

**Retune the compaction `thresholdRatio`/`retainTokens` pair for the new, lower prompt floor** (closed, no change made). The reduced tool surface already eliminated observed compaction churn as a side effect (0/0/0/0/0 compactions across the tool-surface-only sample versus 7/0/0 at baseline), with 6801 tokens of headroom to the context ceiling in the worst observed case. The two conditions that would have reopened this — a longer/heavier run introduced by the model-comparison lever or the decomposition lever — both resolved without adding load: the model-comparison lever was cancelled, and the decomposition lever was rejected together with the prompt-floor increase that would have created the load. The default `0.7`/`6144` pair was left unchanged.

## Consequences

The accepted configuration trades tool surface for reliability on this specific model: subagent delegation, workflow orchestration, goal tracking, web search/fetch, and skill loading are unavailable through this preset, so tasks that genuinely need them must switch presets by hand. In exchange, the measured configuration removed compaction churn entirely in every tool-surface sample collected, cut the model's own `run_code` syntax-error rate roughly in quarter to threequarter across the two levers, and matched or beat the baseline's median wall time in every accepted configuration.

This workload's own run-to-run spread reaches roughly 180% at n=5 even in the final accepted configuration (one persona run hit four compactions and a 1264.2s wall time against a 496.2s median). A regression check against this preset should treat a single slow or compaction-heavy run as expected variance, not a signal, and instead watch the aggregate gate rate and the metric each future change specifically targets, per the general procedure in the linked cookbook page.

The literal 3-consecutive-run acceptance criterion originally written for this preset's consolidation node could not be executed as written: the headless/bench measurement surface used for every lever in this decision does not mount the `agent-presets` service at all, so the packaged preset itself cannot be driven through the same scripted harness used to measure its constituent levers. This was resolved, with the user's explicit agreement, by treating the 5 real `local-fast`+`persona` runs already collected as substitute evidence — the packaged preset patches the identical ids with the identical config values, verified id-for-id against the installed standard composition, so the overlay-driven measurements and the packaged preset are the same effective configuration reached through different composition mechanisms, not two different configurations that merely resemble each other.
