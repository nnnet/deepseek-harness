# Находки — оптимизация dsh на локальной qwen3.8-27b

Рабочий журнал открытий по ходу `.claude/plans/2026-08-27T20-36__dsh-local-qwen38-optimization.md`. Пополняется по мере прохождения графа; не переоткрывать зафиксированное здесь. Краткая версия для возобновления сессии — `.claude/HANDOFF.md`; здесь — полная, с обоснованиями.

## Архитектура харнеса

- **Headless-поверхность (`dsh --profile <любой>` без Web/ACP) не монтирует и не читает агентные пресеты вообще.** Создаёт `Agent` напрямую через core registry (`apps/cli` headless driver), минуя сервис `agentPresets`. Потребители сервиса — только `packages/host/apiproxy`, `packages/client/ui-agent-preset`, `packages/subagent/subagent/src/child-agent.ts`. Следствие: `agent-presets.default` в `settings.yaml` не действует на headless/bench-прогоны, даже если строка `agent-presets` присутствует в композиции профиля и `defaultId` читается корректно, если спросить сервис напрямую (`packages/preset/agent-presets/src/index.ts:191-192`). Рычаги для bench-прогонов ведутся `--patch`-оверлеями (`bench/overlays/*.yml`), не пресетами.
- **Вставка новой строки в патч-слое — ключ `insert` со списком**, не запись верхнего уровня с `id`. Запись `- id: <x>` целится в СУЩЕСТВУЮЩУЮ строку для мержа/переопределения; для отсутствующего id загрузчик пишет в stderr `patch: entry "<id>" not found` и молча ничего не монтирует (процесс не падает). Референс — `packages/bundle/web-app/cordis.patch.yml:441`.
- **`--dump-config` не резолвит модули и не вычисляет `!!js`** (`apps/cli/src/dump-config.ts:30`, `runDumpConfig()`). Строит композицию патч-слоёв структурно. Как проверка «плагин реально существует/грузится/работает» — бесполезен; годится только для проверки, что строка вообще появилась в композиции (включая диагностику `entry "<id>" not found` из предыдущего пункта, которая уходит в stderr этой же команды).
- **`dsh` пишет в каталог профиля на каждом старте**: `prepareProfile()` (`apps/cli/src/profile-boot.ts`) делает `writeFileSync` в `cordis.yml` профиля. Под Bash-песочницей это `EROFS: read-only file system`. Все вызовы `dsh` в этом окружении — только с `dangerouslyDisableSandbox: true`.
- **Пакеты `@deepseek-ai/dsh-*` и локальные для профиля (`dsh-rlm-mode`) резолвятся через `import.meta.resolve()` только из корня профиля** (`~/.dsh/profiles/<name>/`) — там их видят hoisted `node_modules` и общий фоллбэк `~/.dsh/profiles/node_modules`. Из произвольного рабочего каталога (например `~/.dsh/bench-workspace/`) — не резолвятся. Эталонная задача A1 поэтому требует от генерируемого плагина нулевых зависимостей, кроме встроенного в Node.
- **Стандартный пресет контрибутит строки инструментов, а не реестры.** Нельзя примонтировать его поверх headless «для сравнения» — столкнётся с уже смонтированными строками headless.
- **Плагин с одновременно именованным экспортом (`name`/`inject`/`apply`) и default-экспортом** — загрузчик берёт default и молча отбрасывает namespace вместе с `inject` (постмортем `docs/postmortem/0001-acp-default-export-drops-inject.md`). Синтаксически безупречный, статически неотличимый от рабочего плагина код, который просто не регистрирует инструмент. Вошёл в гейт A1 как `bench/broken/mixed-export`.

## Схема журнала сессии (`~/.dsh/sessions/*/*/session.jsonl.zstd`)

- Формат: `zstd`-сжатый JSONL. Первая строка — `{"type":"session", version, id, createdAt, cwd, agentPreset}` без `data`. Дальше построчно `{type, seq, time, data}`.
- **Метаданные сессии несут метку времени СОЗДАНИЯ сессии, не текущего хода.** У переиспользованной/резюмированной сессии `permission/preset`/`sandbox/mode`/`approval/policy` (первые строки после заголовка) датированы моментом первого создания — может быть на дни раньше фактической работы. Границу «от первого события до последнего» для `wall` использовать НЕЛЬЗЯ — даёт вздутое на порядки число (проверено: 254087 с вместо реальных 4516 с на сессии `1db0ee02`). Верная граница — `min(turn/start.time) … max(turn/end.time)`.
- Число входных токенов запроса — в `assistant/chunk` событиях, где `data.chunk.type == "usage"`: `data.chunk.usage.{inputTokens,outputTokens}`. Одно такое событие на шаг (совпадает с числом `step/start`).
- Число шагов — счётчик событий `step/start` (совпадает с `step/end`).
- Число компакций — счётчик событий `compaction/start` (совпадает с `compaction/end`); `compaction/summary` и `compaction/prune` — детали одной компакции, не считать отдельно.
- Доля рассуждений — события `reasoning-chunks` и `text-chunks` — это батчи из нескольких токенов (`data.texts: string[]`), не по одному на событие. Подсчёт по числу СОБЫТИЙ и подсчёт по суммарной длине `texts` дают практически идентичное отношение (проверено на `1db0ee02`: 0.9248 по событиям против 0.9240 по токенам) — можно считать по событиям, дешевле.
- Ошибка инструмента — `tool/result.data.message.content[].isError === true` на блоке `type: "tool-result"`. Число `tool/call` и `tool/result` может не совпадать (доп. диспетчерские события `tool/code-dispatch*` для ipython) — считать ошибки по `tool/result`, не по `tool/call`.

## LM Studio — рассуждающие настройки

- `reasoning_effort` и `chat_template_kwargs` через OpenAI-совместимый API LM Studio **вырезаются**. Ручки в API dsh (`reasoningEfforts` в `settings.yaml`) на локальный маршрут не действуют — оставлены только ради единообразия с `openrouter`.
- Единственный работающий путь — вкладка Inference в самой LM Studio:
  - Custom Fields → Reasoning Effort = Low
  - Custom Fields → Enable Thinking = вкл
  - Custom Fields → **Preserve Thinking = ВЫКЛ** (иначе рассуждения всех прошлых ходов ассистента едут в каждый следующий запрос — раздувает промпт пропорционально числу ходов)
  - Reasoning → Reasoning Budget = 1024 (потолок токенов на мысль)
- Значения живут в LM Studio preset; несохранённый пресет («Unsaved Preset») не переживает перезапуск LM Studio. Пользователь сохранил его 2026-08-27 под именем `Qwen_3_8_reasoning_low`.
- Модель адресуется голым ключом `qwen/qwen3.8-27b`. Суффикс `@q4_k_m` — форма вывода `lms ls`, не идентификатор: `lms load qwen/qwen3.8-27b@q4_k_m` отвечает `Model not found`, API — `Failed to load model`. Квант выбирается в самой LM Studio; `lms ps` подтверждает загруженный вариант по столбцу SIZE (17.74 ГБ = Q4_K_M, 23.36 ГБ = Q6_K).

## A4/bench/run.sh — прогон против реальной LM Studio

- **Проверка LM Studio/`dsh` без host-escalation даёт ложноотрицательный результат.** Bash-песочница разрешает сеть только на `raw.githubusercontent.com`/`github.com`; `curl 127.0.0.1:1234`, `ss -tlnp`, `lms ps` без `dangerouslyDisableSandbox: true` возвращают пусто/timeout независимо от реального состояния LM Studio. Не доверять такой проверке ни разу — всегда повторять с эскалацией перед выводом.
- **Кодировка каталога-ключа сессии по cwd** (`~/.dsh/sessions/`) — это `--` + `cwd` БЕЗ ведущего `/`, с заменой оставшихся `/`→`-`, + `--`. `sed 's#/#-#g'` на пути как есть (с ведущим `/`) даёт лишний дефис спереди (`---home-...` вместо `--home-...--`) — обнаружено первым реальным прогоном `run.sh`: `dsh` завершился штатно (exit 0, 1591 с) и создал сессию по верному пути, скрипт вычислил неверный, `mkdir -p` его создал пустым и не нашёл результат. Метрики того прогона восстановлены вручную из фактической сессии, повторный дорогой инференс не потребовался. Исправление в `run.sh`: `${WORKSPACE#/}` перед `sed`.
- Первый реальный baseline-прогон на живой `qwen/qwen3.8-27b` (LM Studio, Q4_K_M): `wall=1589.6с steps=29 in_med=39592 in_max=54469 think_ratio=0.8331 tool_err=1 compactions=7 gate=1`. Против исторического необъективного `1db0ee02` (`think_ratio=0.9248 compactions=20`) это уже настроенная конфигурация (Reasoning Budget 1024, Preserve Thinking выкл, порог компакции 0.7/пол 34k) — не «до/после» одного рычага, а состояние на старте цикла B1.
- **B1 закрыт, все три прогона `gate=1`.** `wall`: 1589.6с / 617.7с / 671.4с; разброс (max−min)/min = 157 % — далеко за порогом 50 % из плана. Правило сработало: с `C1` и далее каждый цикл рычага — 5 прогонов, не 3. Первый прогон — вероятный выброс (29 шагов, 7 компакций, 1 ошибка инструмента против 16-18 шагов/0 компакций/0 ошибок у прогонов 2-3); природа выброса не диагностирована (сэмплинг vs системный эффект типа холодного кеша) — не блокирует переход к рычагам, но стоит помнить при интерпретации будущих циклов.
- После B1 свободны (needs закрыты, зоны не пересекаются): `C1` (`bench/overlays/local-fast.yml`), `C2` (правка в GUI LM Studio, зона пуста), `C4` (`~/.dsh/settings.yaml`). Можно вести параллельно.

## C1 — второй баг в run.sh: `--` не срезался, затем относительный путь оверлея

Первый прогон 5 реальных задач с `local-fast.yml` (фон `bcxyuzebw`) провалился
все 5 раз мгновенно (`elapsed=0s`), не дойдя до модели: usage-комментарий
`run.sh` документирует форму `[-- --patch extra-overlay.yml ...]`, но код
`EXTRA_PATCH_ARGS=("$@")` после одного `shift` никогда не срезал сам литерал
`--` — он летел дальше в `dsh` как есть, и парсер `dsh` спотыкался об него,
выдавая `error: unknown option '--patch'`. Исправлено добавлением
`[ "${1:-}" = "--" ] && shift` перед сборкой `EXTRA_PATCH_ARGS` в
`bench/run.sh` (строка после LABEL/shift).

После этого фикса вскрылся второй, независимый баг — уже не в `run.sh`, а в
моём вызове: я передал оверлей относительным путём
(`bench/overlays/local-fast.yml`), а `dsh` резолвит `--patch`-пути
относительно СВОЕГО cwd (рабочего каталога прогона,
`~/.dsh/bench-workspace`), не относительно каталога, из которого запущен
`bench/run.sh`. `BASE_OVERLAY` в скрипте всегда абсолютный
(`$BENCH_DIR/overlays/rlm-mode.yml`, вычислен через
`REPO_ROOT="$(cd ... && pwd)"`) — именно поэтому первый оверлей всегда
проходил, а второй, переданный мной relative, падал с `ENOENT`. Исправлено
без правки скрипта — вызов заменён на абсолютный путь
(`"$REPO_ROOT/bench/overlays/local-fast.yml"`).

Второй фикс подтверждён живым прогоном: `dsh` принял оба оверлея и дошёл до
инференса (лог `run.sh: label=local-fast ... overlay=.../rlm-mode.yml
extra=--patch .../local-fast.yml`, без мгновенного `exit=1`). Пять прогонов
идут в фоне (`bzee5jdjz`).

Абсолютное число из плана к `bench` неприменимо; относительное падение — реальное и измеренное. ## C1 — рост tool_err разобран: не отказ инструмента, обычный run_code-баг

`tool_err` вырос `0.33` (baseline) → `0.8` (local-fast, среднее на 1/0/1/2/0). Три сессии с ошибками (`session-534cfa28`, `session-5445f978`, `session-1d43a091`) распакованы (`zstd -dc session.jsonl.zstd`), события `tool/result` с `isError: true` прочитаны напрямую. Ни одна ошибка не связана с погашенными в C1 инструментами (`tool-subagent*`, `tool-workflow`, `tool-goal`, `tool-web`, `tool-skill`) — это ошибки в Python-коде, который модель сама пишет в одну dashr-ячейку (`run_code`):

1. `SyntaxError: unterminated string literal` — незакрытая строка в сгенерированном коде.
2. `TypeError: '>' not supported between instances of 'int' and 'str'` — сравнение разнотипных значений.
3. `NameError: name 'true' is not defined` — модель написала JSON/JS `true` вместо Python `True`.

Тот же класс, что историческая находка `.claude/HANDOFF.md`: «151 отказ `run_code`, все синтаксические». Причинной связи с сокращением поверхности инструментов (C1) нет. Рост на выборке n=5, вероятно, шум сэмплинга — сравнивать доверять только на большей выборке. Три класса ошибок легли прямым текстом в `bench/overlays/persona.yml` (узел C6): запрет на многофайловые правки/длинный код за ячейку, обязательный `print` промежуточного результата, явное требование `True`/`False`/`None`.

5 реальных прогонов эталонной задачи с `bench/overlays/persona.yml` поверх `local-fast.yml`, все `gate=1`. Сравнение с 5×`local-fast` (`bench/ledger.md`):

|---|---|---|---|
| `tool_err` среднее | 0.8 (1/0/1/2/0) | **0.2** (0/0/0/1/0) | **−75 %** |
| `wall` медиана | 628.7с | **496.2с** | −21 % |
| `wall` среднее | 600.5с | 694.9с | +16 % (перекошено выбросом) |
| `compactions` | 0/0/0/0/0 | 0/0/0/0/4 | 1 выброс |
| `in_med` / `in_max` | 29053.9 / 42660.8 | 30429.9 / 39889.8 | без значимого сдвига |
| `steps` среднее | 21.4 | 20.4 | без значимого сдвига (план ожидал рост — не подтвердилось и не опровергнуто) |

`tool_err` падает ровно в целевом направлении (0.8 → 0.2) — согласуется с тем, что все три исходных ошибки были из класса, на который целится персона (см. предыдущую находку). Один прогон persona (`session-5d055a6d`, wall=1264.2с, compactions=4) — выброс, тянущий среднее `wall` вверх; медиана при этом лучше baseline `local-fast`. Механизм правдоподобен и симметричен с историческим выбросом `baseline`-run1 (`steps=29`, `compactions=7`, самый долгий `wall` в той выборке): каждая компакция — отдельный дорогой вызов суммаризации, и именно прогоны с ненулевыми компакциями оказываются самыми медленными в обеих выборках. Причина, почему именно этот прогон пробил порог — не установлена: персона добавляет заметный кусок текста к системному промпту (сравнимого не измерено отдельным пробником), что при ~20 ходах даёт небольшую кумулятивную добавку, но с n=1 выброс неотличим от той же случайной вариативности, что уже задокументирована в B1 (157% разброс `wall` на baseline).

Рычаг **принят**: основная цель C6 (снизить `tool_err`, не отказы инструментов) достигнута видимым, объяснимым эффектом; побочный компакционный выброс на одном прогоне из пяти не опровергает эффект и не блокирует приёмку, но стоит держать в уме при будущей калибровке текста персоны (короче — меньше кумулятивная добавка).

## C2 — отклонён: Reasoning Budget 512 хуже 1024 по всем метрикам, 256 не тестировали

Свип начат с текущего значения `Reasoning Budget = 1024` (уже валидировано 5×`persona`-прогонами из C6) вниз к `512`, стек `local-fast` + `persona` неизменен, менялось только поле Reasoning Budget в GUI LM Studio (ручное переключение — нет API-пути, см. узел C2 в плане). 5 реальных прогонов на `512`, `gate.mjs` — не заглушка.

| метрика | 1024 (n=5, из C6) | 512 (n=5) |
|---|---|---|
| `wall` среднее / медиана | 694.9с / 496.2с | **1428.4с** / **1129.7с** |
| `compactions` среднее | 0.8 (0/0/0/0/4) | **6.6** (19/0/3/11/0) |
| `gate` | 5/5 | **4/5** |
| `tool_err` среднее | 0.2 | **1.6** |
| `in_max` худший | 48901 | **65453** (83 токена до потолка 65536) |

Направление однозначное и одинаковое на всех пяти метриках — нет ни одной, где `512` лучше или хотя бы нейтрален. Правдоподобный механизм: обрезанное вдвое бюджет рассуждения не даёт модели закончить мысль за один проход, что провоцирует повторные попытки/более длинные диалоги вместо линейно более короткого рассуждения — отсюда рост `compactions` и `wall` вместо ожидаемого падения. Один прогон (`session-a95987a7`, `in_max=65453`) почти пробил потолок окна `65536` — 83 токена запаса, ближе к отказу, чем любой прогон во всей истории `ledger.md`.

`256` **не тестировали**: при однозначно отклоняющем сигнале на всех пяти метриках у `512` дальнейшее снижение бюджета с тем же причинным механизмом почти наверняка ухудшит результат ещё сильнее — трата ещё ~1ч реального инференса не изменила бы вывод. Это инференс из наблюдаемого тренда, не отдельный реальный прогон; если он не подтвердится позже — переоткрыть узел, не полагаться на эту находку как на протестированный факт для `256` конкретно.

Рычаг **отклонён**: наименьшее значение, при котором `gate=1` держится на всех прогонах — уже `1024` (без изменений от текущего состояния). Приёмка узла C2 выполнена этим выводом; действие для пользователя — вернуть Reasoning Budget обратно на `1024` в GUI LM Studio.

## Инфраструктурные ловушки

- **`pkill` по пути процесса не находит `dsh`**: `dsh` — симлинк, Node оставляет в `argv[1]` `/usr/local/bin/dsh`. Останавливать по слушающему порту через `ss`.
- **`supportedArchitectures` читается только из `pnpm-workspace.yaml`**. Форма `supported-architectures.*` в `.npmrc` под pnpm 11 игнорируется (проверено дифференциально).
- **pnpm 11 требует явного `allowBuilds`** для нативных пакетов со скриптами сборки (например `zeromq`, транспорт `ipykernel` для `dsh-rlm-mode`) — иначе `[ERR_PNPM_IGNORED_BUILDS]` останавливает `pnpm install`. Профили `web` и `bench` держат `allowBuilds: { zeromq: false }`.
- **`compaction-basic` отключён в профиле `web` намеренно** (`dsh-web-app`): бэкенд компакции живёт в плоскости пресета там, где пресеты вообще монтируются. Правки — в `agent.cordis.yml` пресета для Web UI; для `bench` — напрямую на живой строке хоста, так как пресетов там нет (см. архитектурный пункт выше).
- Модель для суммаризации компакции не задавать явно: пустая пара берёт маршрут последнего запроса и переиспользует прогретый KV-префикс; смена модели его обнуляет.
- `fatal: not a git repository` при старте Web UI — опрос зарегистрированных рабочих каталогов; `Workspaces/WS_03`/`WS_04` не репозитории. Решение за пользователем (`git init` либо убрать из списка).
